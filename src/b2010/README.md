# Бот пробою 20/10 (BTCUSDT, Bybit)

Детермінований бот без моделі: денний пробій 20-денного каналу, стоп за 10-денним каналом, без тейк-профіту. Працює локально через CLI, окремо від застосунку на Cloudflare. Код: `src/b2010/`, CLI: `scripts/b2010.ts`, тести: `test/b2010*.test.ts`.

Це інструмент для перевірки стратегії, а не фінансова порада.

## Правила

- **Контракт**: BTCUSDT linear USDT perpetual, свічки 1D за UTC, лонг і шорт, одна позиція, one-way, плече 1x, без усереднення.
- **Вхід**: t — денна свічка, що щойно закрилась. `upper20` / `lower20` — найбільший High / найменший Low свічок t-20…t-1 (t не входить). Close[t] > upper20 — лонг, Close[t] < lower20 — шорт. Рівність, дотик і пробій тінню входу не дають. Потрібна 21 послідовна завершена свічка. За відкритої позиції сигнали ігноруються.
- **Час входу**: перша ціна після закриття t. Бектест — Open[t+1] з несприятливим прослизанням; paper — ask для купівлі, bid для продажу; testnet/live — ринковий ордер. Вікно входу — 120 с від початку доби (`B2010_ENTRY_WINDOW_SEC`), далі сигнал прострочений.
- **Стоп**: на початку t+1 — мінімальний Low (лонг) / максимальний High (шорт) свічок t-9…t, до кроку ціни (лонг вниз, шорт угору). Якщо ціна вже за стопом — вхід пропускається. Після кожного денного закриття стоп = max/min(чинний, канал 10 днів), лише в бік зменшення ризику. Спрацювання — за LastPrice, цілодобово. Якщо новий рівень уже пройдено — закриття через reduceOnly.
- **Розмір**: `riskBudget = equity × 0.005`, `lossPerBTC = |E − X| + E·f + X·f`, `qty = riskBudget / lossPerBTC`; обмеження маржею (1x, резерв на комісії) і `maxMktOrderQty`, округлення **вниз** до `qtyStep`. Менше за `minOrderQty` / `minNotionalValue` — угода пропускається з причиною; вгору до мінімуму не округлюється. Equity — лише капітал бота (`B2010_BALANCE` плюс його результат), кошти інших стратегій розмір не збільшують.

0.5% — плановий ризик: геп, затримка виконання та фандинг можуть збільшити фактичний збиток.

## Команди

```bash
npm install
npm test                                   # усі тести, зокрема test/b2010*.test.ts
cp .env.example .env                       # налаштування й ключі (ключі лише для testnet/live)

npm run b2010 -- download                  # історія Bybit у .b2010/cache
npm run b2010 -- backtest                  # увесь період, до контрольного й контрольний
npm run b2010 -- backtest --from 2021-01-01 --to 2026-10-31
npm run b2010 -- paper                     # paper на публічних даних mainnet (Ctrl+C — зупинка)
npm run b2010 -- status                    # позиція, блокування, сигнали, події
npm run b2010 -- export --out trades.csv   # журнал угод paper у CSV

npm run b2010 -- testnet                   # потрібні BYBIT_TESTNET_API_KEY / _SECRET
npm run b2010 -- status --mode testnet
npm run b2010 -- live --confirm-live       # реальні гроші: ще B2010_LIVE_ENABLED=yes і BYBIT_API_KEY / _SECRET
```

Bybit не відповідає з деяких країн (США тощо: HTTP 403 від CloudFront) — тоді запускайте з дозволеної країни.

## Бектест

Дані з публічного API Bybit V5: денні й годинні свічки BTCUSDT perp, годинні свічки ціни маркування, історичні ставки фандингу, денні свічки споту BTCUSDT (для порівняння з купівлею BTC). Кеш помісячний (`.b2010/cache`), поточний місяць завантажується знову. Перевіряються порядок, повтори й пропуски; пропуск денних свічок у періоді зупиняє бектест і друкує, які дати неможливо перевірити.

Порядок подій без підглядання: вхід на старті доби бачить лише попередні завершені свічки; стоп, чинний на початок доби, спрацьовує, якщо Low ≤ стоп (лонг) / High ≥ стоп (шорт), зокрема в день входу; якщо доба відкрилась за стопом — вихід за Open; новий стоп після закриття діє лише з наступної доби. Комісія — на кожне виконання (типово 0.055% taker), прослизання — несприятливе (типово 0.05%, окремо подвійне). Фандинг — за історичними ставками в моменти нарахування, вартість позиції — за ціною маркування; додатна ставка — лонг платить, шорт отримує. Якщо стоп і нарахування в одній добі, порядок уточнюється годинними свічками; нарахування в годині стопа неоднозначне — враховується лише як витрата. Сьогоднішні обмеження ордера (`tickSize`, `qtyStep`, `minOrderQty`, `minNotionalValue`) застосовуються до всієї історії: датованих API не дає — звіт про це пише.

Звіт (консоль і `.b2010/out/<from>_<to>/`): дати, капітал на старті й кінці, результат у USDT і %, окремо ціновий результат, прослизання, комісії й фандинг (сума складників дорівнює результату), максимальна просадка за денною equity з відкритою позицією, угоди, частка прибуткових, середній прибуток і збиток, найдовша серія збитків, лонг і шорт окремо, сигнали, входи й пропуски за причинами, купівля BTC на споті тим самим капіталом, позиція на кінець. Періоди: повний, до контрольного й контрольний — останні 12 повних місяців (свій стартовий капітал, канали розігріваються попередніми свічками; параметри 20/10 за ним не підбираються). Файли: `report.txt`, `report.json`, `trades-*.csv`, `signals-*.csv`, `equity-*.csv`.

**Чого чекати від 500 USDT.** Мінімальний ордер BTCUSDT — 0.001 BTC. При ризику 2.5 USDT угода можлива, лише якщо збиток до стопа з комісіями не більший за 2 500 USD на 1 BTC, тобто стоп ближче ~2.5–3% від ціни за BTC близько 90 000. Стоп за 10-денним каналом зазвичай далі, тож на дорогому BTC більшість сигналів пропускаються з причиною `qty_below_min`. Правила від цього не змінюються: щоб угоди були, потрібен більший капітал бота (`B2010_BALANCE`).

## Paper, testnet, live

Усі режими — той самий рушій (`runner.ts`) і ті самі функції сигналу, стопа й обсягу; різниться лише виконання (`paper.ts` або `bybitBroker.ts`). Стан — SQLite (`.b2010/<режим>.sqlite`, вбудований `node:sqlite`): сигнали, наміри ордерів, угоди, виконання, фандинг, події, денна equity.

- **Paper** (за замовчуванням): публічні дані mainnet без ключів. Купівля за ask, продаж за bid, стоп за LastPrice, фандинг за ставкою й ціною маркування. Якщо процес був вимкнений, стоп «на біржі» відновлюється за хвилинними свічками.
- **Testnet / live**: перед входом — режим позиції (one-way), плече 1x, баланс; стороння позиція чи невідомий ордер по BTCUSDT зупиняють нові входи (чужою позицією бот не керує). Ордер входу — ринковий з `stopLoss`, `slTriggerBy=LastPrice`, `tpslMode=Full`: стоп живе на біржі й працює, коли бот вимкнений; далі стоп рухається через Set Trading Stop.
- **Намір і orderLinkId**: перед відправленням намір пишеться в SQLite; `orderLinkId` стабільний для сигналу (`b2010-YYYYMMDD-L|S`). Таймаут — стан невідомий: спершу перевірка на біржі, нові входи заблоковані до звірки. Розмір і середня ціна — за фактичними виконаннями; залишок частково виконаного входу не добирається.
- **Захист**: після виконання звіряються позиція й біржовий стоп; якщо стопа немає й поставити не вдалося — належний боту залишок закривається reduceOnly з критичною подією. За обриву зв'язку незавершений намір лишається в БД, звірка повторюється після відновлення.
- **Рестарт**: звірка позиції, ордерів, виконань і стопа; пропущені денні свічки обробляються по черзі (стоп підтягується), пропущені сигнали позначаються простроченими — позиції заднім числом не відкриваються.
- **Один процес** на режим і символ (файл-замок `.b2010/<режим>-BTCUSDT.lock`).
- **Live** лише за трьох умов: команда `live`, прапорець `--confirm-live`, `B2010_LIVE_ENABLED=yes`. Спершу — testnet. Ключ — лише з правом торгівлі, без виведення.

Не перевірено на біржі: testnet і live (зокрема знак поля `funding` у журналі транзакцій і поведінка `stopLoss` на ринковому ордері при частковому виконанні); paper і бектест на живому API Bybit (з хмарного середовища розробки API недоступний, перевірено лише на архіві годинних свічок public.bybit.com).
